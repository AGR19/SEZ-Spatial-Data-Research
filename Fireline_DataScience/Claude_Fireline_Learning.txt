CLAUDE FIRELINE LEARNING — Coding Style & Research Pipeline Patterns

Synthesized from three Fireline DataScience research sub-projects:
  1. Learning flow simulator (Shiny for Python dashboard)
  2. ARC-GIS-datascience-main (GIS + school data analysis, Jupyter notebooks)
  3. koch_research-consolidate (R + Python statistical analysis, SEM modeling)

This document captures actionable coding rules and research pipeline patterns
to replicate in future code generation.

================================================================================
A. R CODING CONVENTIONS (from sem.R, sem_real.R)
================================================================================

1. PACKAGE LOADING
   - All library() calls at the top of the script, before any data work
   - Group by purpose: statistical, data manipulation, visualization
   - Example:
       library(lavaan)       # SEM modeling
       library(semTools)     # SEM diagnostics
       library(corrplot)     # Correlation matrices
       library(psych)        # Descriptive statistics
       library(ggplot2)      # Visualization
       library(dplyr)        # Data manipulation
       library(gridExtra)    # Multi-panel plots
       library(lavaanPlot)   # SEM path diagrams

2. REPRODUCIBILITY
   - Always set.seed(42) immediately after library loading
   - This ensures any randomized processes are replicable

3. VARIABLE NAMING
   - snake_case throughout: growth_mindset_latent, prior_knowledge, course_activity
   - Composite variables use descriptive suffixes: gm_composite, gm_pk_interaction
   - Model objects use the pattern: cfa_fit, sem_fit, sem_fit_mod, sem_fit_activity
   - Data frames: just "data" for the main working frame, prefixed when multiple

4. COMMENTING STYLE (Critical — replicate this exactly)
   - Section headers use triple-equals blocks:
       # === SECTION NAME ===
   - Sub-sections use short comments above code blocks:
       # Basic SEM model
       # Fit CFA model
       # Factor loadings
   - Inline reasoning comments when making judgment calls:
       # I think these are outliers
       # These two models use different pk measures
   - Model specification strings use inline comments for clarity:
       sem_model <- '
         # Measurement model
         growth_mindset =~ GM1 + GM2 + GM3 + GM4 + GM5 + GM6 + GM7 + GM8

         # Structural model
         course_activity ~ b1*growth_mindset + b2*prior_knowledge

         # Indirect effects (mediation)
         indirect_gm := b1 * c3
       '
   - Divider lines for major new analysis sections:
       ##################NEW ANALYSES USING FIT INDICES######################################
       #############################

5. STRUCTURED CONSOLE OUTPUT
   - Use cat() with === delimiters for section labels:
       cat("=== DATA OVERVIEW ===\n")
       cat("Sample size:", nrow(data), "\n")
   - Include interpretation thresholds inline:
       cat("CFI:", round(fit_measures["cfi"], 3), "(> 0.95 = excellent, > 0.90 = acceptable)\n")
       cat("RMSEA:", round(fit_measures["rmsea"], 3), "(< 0.05 = excellent, < 0.08 = acceptable)\n")
   - Effect size classification with human-readable labels:
       magnitude <- ifelse(effect_size < 0.1, "trivial",
                     ifelse(effect_size < 0.3, "small",
                       ifelse(effect_size < 0.5, "medium", "large")))

6. DATA MANIPULATION
   - Use dplyr pipe and rename for column transformations:
       data <- data %>% rename(`course_engagement` = `log10.engagements.`)
   - Subsetting with negative indexing for outlier removal:
       data <- data[-c(30,118,8,202,220,52,78,252,92,209,186,147),]
   - Composite scores via rowMeans:
       data$gm_composite <- rowMeans(data[, paste0("GM", 1:8)])
   - Interaction terms as explicit column creation:
       data$gm_pk_interaction <- data$gm_composite * data$prior_knowledge

7. STATISTICAL MODELING WORKFLOW
   Step 1: Define model as a multiline string with comments
   Step 2: Fit model with explicit estimator choice
   Step 3: Print summary with fit.measures=TRUE, standardized=TRUE
   Step 4: Check modification indices if fit is poor
   Step 5: Respecify model, refit, compare
   Step 6: Visualize path diagram + individual plots

   - Iterative model refinement is the norm — keep earlier models visible

8. VISUALIZATION PATTERNS (ggplot2)
   - Always use theme_minimal()
   - Reference lines for cutoffs: geom_hline(yintercept = 0.7, linetype = "dashed")
   - Color coding for significance: scale_fill_manual(values = c("Significant" = "darkgreen", "Non-significant" = "gray"))
   - coord_flip() for horizontal bar charts
   - geom_text() annotations with significance stars
   - grid.arrange() for multi-panel layouts
   - lavaanPlot for SEM path diagrams with node_options and edge_options

9. FUNCTION DESIGN
   - Wrap reusable visualization into functions:
       plot_sem_summary_plots <- function(sem_fit, title_prefix = "SEM Model") {
         ...
         return(list(paths_plot = path_plot, loadings_plot = loadings_plot))
       }
   - Return named lists from functions for flexible downstream use


================================================================================
B. PYTHON/GIS CONVENTIONS (from ARC-GIS notebooks)
================================================================================

1. IMPORT STYLE
   - Standard library first, then third-party:
       import numpy as np
       import pandas as pd
       import matplotlib
       matplotlib.use("Agg")
       import matplotlib.pyplot as plt

2. DATA LOADING
   - ALWAYS specify dtype explicitly to prevent type inference errors:
       df_locs = pd.read_csv("geo_locs.csv", index_col=False, dtype={
           'NCESSCH': str,
           'LEAID': str,
           'LAT': str,
           'LON': str,
       })
   - Convert types after loading:
       df_locs_dir_tot.LAT = df_locs_dir_tot.LAT.astype(float)

3. SECTION MARKERS
   - Use decorated comment blocks:
       # -- CATEGORY METADATA -----------------------------------------------
       # -- DATA LOAD --------------------------------------------------------
       # -- CHART HELPERS ----------------------------------------------------
       # -- UI ---------------------------------------------------------------
       # -- SERVER -----------------------------------------------------------

4. CONSTANTS
   - UPPERCASE for configuration values defined at module level:
       CATEGORIES = ["escape_char", "list_syntax", "string_delim"]
       PASS_COLOR = "#1D9E75"
       FAIL_COLOR = "#E24B4A"

5. NAMING
   - snake_case for everything: df_eval, base_pct, ft_pct
   - DataFrames: descriptive prefixes (df_locs, df_locs_dir, school_totals)
   - Functions: descriptive snake_case (chart_category_bars, chart_outcome_donut)
   - Private helpers prefixed with underscore: _style()

6. DATA TRANSFORMATION PIPELINE
   - pd.merge() on standardized keys for multi-table joins
   - pd.pivot_table() for restructuring:
       pd.pivot_table(values='STUDENT_COUNT', index=[...], columns=[...], aggfunc=np.sum)
   - Chained filtering:
       df[df['STUDENT_COUNT'] != 0][df['RACE_ETHNICITY'] != 'No Category Codes']

7. QUALITY CHECKS
   - Always verify uniqueness after joins:
       len(set(school_totals.NCESSCH)) - len(school_totals.NCESSCH)
   - Reconciliation totals:
       base_tot - fil_tot
   - Print row counts at each ETL step

8. EXPORT STRATEGY
   - Multiple formats for different downstream uses:
       df.to_parquet("school_internet_2.gzip", compression='gzip')
       df.to_csv("output.csv")
       df.to_excel("output.xlsx")
   - Parquet for compute pipelines, CSV for sharing, Excel for review

9. VISUALIZATION (seaborn + matplotlib)
   - Set theme at session level:
       sns.set_theme(style="white", context="talk")
   - Explicit figure sizes: fig, (ax1) = plt.subplots(1, 1, figsize=(15, 10))
   - Color palettes: palette="viridis"

10. GIS-SPECIFIC PATTERNS
    - Coordinates stored as LAT/LON float columns
    - Spatial joins performed in ArcGIS Pro or GeoPandas (point-in-polygon)
    - CRS handling should be explicit — always document the coordinate system
    - Export merged spatial+tabular data for downstream analysis


================================================================================
C. SHINY APP PATTERNS (from Learning flow simulator)
================================================================================

1. FILE HEADER
   - Multi-line comment block describing the DATA CONTRACT:
     what columns the input data must have, their types, and semantics
   - This ensures anyone reading the code knows the data expectations

2. STRUCTURE
   Top of file:
     1. Header / data contract docstring
     2. Imports
     3. Constants and category metadata
     4. Data load (single parquet read)
     5. Helper functions (chart_*, _style)
     6. UI definition (CSS embedded, layout_columns)
     7. Server logic (reactive.calc, render.ui, render.plot)
     8. App instantiation: app = App(app_ui, server)

3. REACTIVITY
   - @reactive.calc for filtered data
   - @render.ui for computed metric values
   - @render.plot for chart rendering
   - @render.data_frame for interactive tables

4. EMBEDDED CSS
   - CSS defined as a Python string constant at module level
   - Applied via ui.tags.style(CSS)
   - Uses class-based styling (.metric-card, .badge-pass, .badge-fail)

5. SAFE DIVISION
   - Always guard against zero denominators:
       round((br - ftr) / br * 100) if br else 0


================================================================================
D. CROSS-PROJECT RESEARCH PIPELINE TEMPLATE
================================================================================

ALL three projects follow the same high-level pipeline:

  1. DATA INGESTION
     - Load from CSV/parquet/feather with explicit types
     - Document data sources with URLs or file paths
     - Print record counts after loading

  2. DATA CLEANING & VALIDATION
     - Remove NaN/invalid rows
     - Type conversions (string -> float, integer -> factor)
     - Duplicate checks
     - Outlier identification with reasoning comments

  3. DATA TRANSFORMATION
     - Groupby aggregations
     - Pivot tables for restructuring
     - Feature engineering (composites, interactions, distance calculations)
     - Spatial joins where applicable

  4. STATISTICAL ANALYSIS
     - Descriptive statistics first (means, distributions)
     - Model fitting with explicit estimator choices
     - Fit diagnostics reported with interpretation thresholds
     - Effect sizes classified (trivial/small/medium/large)
     - Iterative model refinement based on diagnostics

  5. VISUALIZATION
     - Publication-ready with theme_minimal() / sns.set_theme()
     - Color coding for categorical distinctions
     - Reference lines for cutoff values
     - Multi-panel layouts (grid.arrange / layout_columns)
     - Significance annotations on plots

  6. EXPORT & DOCUMENTATION
     - Multiple output formats (parquet, csv, excel)
     - Summary statistics printed to console
     - Interpretation guidance embedded in output
     - Intermediate results saved for reproducibility


================================================================================
E. KEY RULES TO ALWAYS FOLLOW
================================================================================

  1. Comments should explain WHY, not just WHAT — include reasoning
  2. Section headers are mandatory for code organization
  3. Never suppress warnings silently — investigate and document
  4. Print data dimensions after every major transformation
  5. Use explicit type specifications in all data reads
  6. Save intermediate results for reproducibility
  7. Report fit diagnostics with human-readable interpretation thresholds
  8. Color coding should be semantically meaningful (green=good, red=bad)
  9. Functions should return structured objects (lists, data frames)
  10. Keep earlier model iterations visible — do not delete failed attempts
